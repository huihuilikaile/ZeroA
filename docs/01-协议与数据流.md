# 01 · 协议与数据流

这份文档讲清楚一件事：**Pi 的 RPC 到底是什么样的一条管道，以及为什么代码要那么写。**
读完它再看 `internal/pi/client.go`，每一行注释都会对上。

---

## 1. 一句话概括

Pi 是一个**长驻子进程**。你和它之间只有两根管道：

```text
你的程序  ──stdin（写命令）──▶  Pi RPC 进程
你的程序  ◀─stdout（读响应和事件）──  Pi RPC 进程
           ◀─stderr（只是诊断日志）──
```

- 命令、响应、事件都是 **JSON**；
- 每条记录占 **一行**，用 `\n` 结束 —— 这叫 JSONL（JSON Lines）；
- 一次启动之后，进程一直活着，可以连续问很多条命令。

这就是全部。没有 HTTP，没有 WebSocket，没有端口，没有握手。

---

## 2. 三种记录

| 类型 | 方向 | 有没有 `id` | 含义 |
| --- | --- | --- | --- |
| `command` | 你 → Pi | 有 | “帮我做件事”，例如 `prompt`、`get_state`、`abort` |
| `response` | Pi → 你 | 有，且与命令相同 | “你那条命令我收到/处理了” |
| `event` | Pi → 你 | **没有** | “我这边发生了这件事”，例如正在出字、回合结束 |

真实抓到的三条（①② 来自 `go run ./cmd/rpc-demo -mode real`，
模拟模式只有 `model`/`sessionId` 的值不同，结构完全一样）：

```jsonc
// ① 你发出去的命令
{"id":"req-1","type":"get_state"}

// ② Pi 回的同 id 响应
//    模拟模式里这里是 "model":{"id":"mock-model","provider":"local"}、"sessionId":"mock-session"
{"id":"req-1","type":"response","command":"get_state","success":true,
 "data":{"model":{"id":"deepseek-flash",...},"isStreaming":false,"sessionId":"..."}}

// ③ 事件的形状完全不同：没有 id，只有 type
{"type":"agent_start"}
{"type":"message_update","assistantMessageEvent":{"type":"text_delta","contentIndex":0,"delta":"链"}}
{"type":"agent_settled"}
```

**关键认知：`response` 回答的是“命令”，`event` 描述的是“过程”。**
两者混在同一个 stdout 里，靠 `type` 字段区分，靠有没有 `id` 决定归谁。

---

## 3. 分帧：为什么必须“一行一条、整行写出”

管道是**字节流**，不是消息队列。写进去 100 字节，对面可能分 3 次读到。
所以必须有一条规则把字节流切回一条条消息，这里的规则就是：**换行。**

这条规则带来三个后果，代码里对应三处设计：

**① JSON 里的换行会被转义。**
字符串中的 `\n` 写成 `\\n` 两个字符，所以一条记录内部永远没有真实换行。
切分是安全的。

**② 写入必须整行原子。**
如果两个 goroutine 各写半行，会变成：

```text
{"id":"req-1","type":"pro{"id":"req-2","type":"abort"}mpt"}
```

两行全废。所以 `internal/pi/client.go` 里有一把 `writeMu`：
**同一时刻只有一个完整的“JSON + LF”被写出去。**

**③ 读取要有上限。**
`bufio.Scanner` 默认单行 64 KiB。本 Demo 显式放大到 4 MiB
（`scanner.Buffer(...)`）：既支持大记录，又能在遇到损坏数据时明确失败，
而不是无限吃内存。

> 分帧只认 `LF`（以及 Windows 的 `CRLF`），不认 Unicode 的 U+2028/U+2029。
> 这两个字符可以安全地待在 JSON 字符串里 —— 测试 `TestLargeUnicodeRecord` 就在验证这点。

**stderr 不是协议流。** 它只放日志，所以 `client.go` 里 `direction != "stdout"` 时
只把内容交给观察器，不去解析、也不去唤醒任何请求。

---

## 4. id 关联：为什么不能“发一条等一条”

你可能会想：一个进程、一根管道，那我发一条、等结果、再发下一条不就行了？

可以，但会很脆弱，原因是：

1. **响应可能乱序。** 命令的处理是异步的，先发的命令不一定先回；
2. **事件会和响应混在一起。** 你等 `response` 的时候，中间会插进来几十条 `event`；
3. **现实需求就是并发的。** 比如界面一边等 `prompt` 的响应，一边还要能发 `abort`。

所以正确的做法是：

```text
每条命令生成唯一 id
→ 把 id 和“等待者”登记到一张表（pending）
→ 写命令
→ 等这个 id 的响应（可以设超时）

读取循环收到一行 → 是 response 就按 id 查表 → 交给对应的等待者
```

代码位置：`Client.Request()`（登记、写、等）与 `Client.read()`（查表、投递）。

三个细节值得注意：

- **先登记再写。** 如果先写再登记，Pi 有可能快到你还没来得及登记就回了响应，那条响应会被丢掉、请求一直等到超时。代码里 `c.pending[id] = ch` 在 `stdin.Write` 之前。
- **投递通道带 1 个缓冲。** 调用方可能已经超时离开，此时读取循环不能因为没人接而卡住 —— 卡住就等于整个协议流停了。
- **超时后到达的响应会被丢弃。** 因为超时返回时已经把自己从表里删掉了。这是有意的：迟到的结果没有意义，且不能让下一次请求误配。

## 5. 生命周期：三个时刻不能混淆

界面底部写着一句话，那是这一节的重点：

| 时刻 | 你观察到什么 | 它真正的含义 |
| --- | --- | --- |
| ① 写入 stdin 成功 | `Write` 没报错 | 命令**发出去了**，仅此而已 |
| ② 收到 `response.success=true` | 一条同 id 的响应 | 命令**被接受/处理了**，任务可能刚开始 |
| ③ 收到 `agent_settled` | 一条事件 | 这轮**不会再有后续了**，可以发下一条 |

真实 Pi 一轮的完整事件骨架（本仓库实测）：

```text
agent_start
turn_start
message_start(user)  → message_end(user)
message_start(assistant)
message_update(text_start)
message_update(text_delta) × N     ← 界面就是在这里逐字出字的
message_update(text_end)
message_end(assistant)             ← 权威结果在这里
turn_end
agent_end(messages, willRetry)
agent_settled                      ← 真正的“结束”
```

注意两点：

- **`agent_end` 不等于结束。** 它可能带着 `willRetry=true` 再来一轮，所以
  “正在生成”要等 `agent_settled` 才能关掉。
- **`message_end` 是权威结果。** 流式的 `text_delta` 可能丢、可能重复；
  `message_end` 里是完整的最终消息，所以界面会用它替换掉临时拼出来的文本。

还有一个容易踩的例外：**`prompt` 的 `response.data.disposition == "handled"` 时，
根本不会启动 agent**（被扩展直接处理掉了），也就永远不会有 `agent_settled`。
`cmd/rpc-demo/main.go` 专门为它写了一个提前返回，否则程序会一直等下去。

## 6. 超时不等于取消

这是新手最容易误解的一点。

```text
ctx 超时  =  “我不等了”          → Pi 那边可能还在跑
abort 命令 =  “请停下来”            → 真正让生成停止
Close()   =  “关掉进程”             → 连进程一起结束
```

所以界面上“等待响应超时”时正确的做法是**再发一条 `abort`**，
`cmd/rpc-demo/main.go` 的超时分支就是这么做的。

进程退出的处理则靠 `done` 通道：`Wait()` 完成后关闭它，
所有还在等的请求会立刻从 `case <-c.done:` 返回，而不是等到超时。

---

## 7. 缓冲与背压

管道有内核缓冲区（Windows 上大约 64 KiB）。这意味着：

- **子进程写满缓冲区又没人读 → 它阻塞在写操作上。** 所以 `Start()` 里
  必须在 `cmd.Start()` 之后立刻启动读取 goroutine。
- **你写满缓冲区而 Pi 没在读 → 你的写入阻塞。** 本 Demo 的写入没有绑定 `ctx`
  （代码里有注释说明）：一条超大的记录会一直等到 Pi 读走，或者等到 `Close()`
  在 3 秒后强杀进程把它“顶”回来。这是有意的简化，真实产品需要更细的流控。

另一个坑是 `cmd.Wait()` 的时机：Go 文档明确要求，**先读完 StdoutPipe/StderrPipe
再调用 Wait**，否则 Wait 会关闭管道，把最后几行输出（比如最后的 `agent_settled`）丢掉。
`Start()` 里用 `sync.WaitGroup` 等两个 reader 结束，就是为了这件事。

## 8. 一次完整往返（把上面全部串起来）

```text
界面点击“发送 Prompt”
      │
      │ Wails Binding（前端 → Go）
      ▼
PiService.Prompt(message)
      │  加 15s 超时
      ▼
Client.Request(ctx, "prompt", {...})
      │  ① 生成 id=req-7
      │  ② pending["req-7"] = ch        ← 先登记
      │  ③ writeMu 内写出 {"id":"req-7","type":"prompt",...}\n
      ▼
   ┌── 等待三选一 ──────────────────────────────┐
   │  ch 收到 response   → 命令被接受，返回      │
   │  ctx.Done()        → 超时（任务还在跑）     │
   │  c.done            → 进程退出              │
   └────────────────────────────────────────────┘
                                     同时……
Pi 的事件不断从 stdout 到达 → read() → onTrace 回调
      │
      │ app.Event.Emit("pi:trace", trace)
      ▼
前端唯一监听器 → 解析 → 更新状态 → 逐字渲染
```

## 9. 和 HTTP 的对照（帮助建立直觉）

| | HTTP 请求 | Pi RPC |
| --- | --- | --- |
| 传输 | 一次请求一个连接/流 | 一根长驻管道 |
| 分帧 | 头部 + Content-Length | 一行一条 JSON（LF） |
| 配对 | 一个连接对一次响应 | `id` 字段配对（可乱序） |
| 过程通知 | SSE / WebSocket | 同一根 stdout 里的 event |
| 结束信号 | 响应体结束 | `agent_settled` |
| 取消 | 断开连接 | 发送 `abort` 命令 |

理解了这张表，就理解了为什么本 Demo 的代码长这样。
