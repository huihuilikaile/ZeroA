# 02 · 代码导读

这份文档回答三个问题：**该按什么顺序读、每一层负责什么、想改东西该动哪里。**
配合 [01 · 协议与数据流](01-协议与数据流.md) 一起看效果最好。

---

## 1. 分层与目录

```text
pi-gui-c/
├── main.go                    桌面程序入口：只创建一个 Wails App，装配 Service 与事件转发
├── service.go                 PiService 生命周期、对话 RPC 与统一返回契约
├── sessions.go                会话扫描/切换/改名/删除与工作区默认值
├── providers.go               Provider、凭据、打开路径与导出
├── attachments.go             附件、粘贴图片与模型配置
├── files.go                   工作区文件树与文本预览
├── bindings_test.go           检查生成的 TS 绑定与 Service 方法是否同步
├── cmd/rpc-demo/main.go       命令行入口：最短的一条完整调用链
├── internal/
│   ├── pi/                    ★ 协议层，不 import Wails/React
│   │   ├── client.go          进程、JSONL 分帧、id 关联、超时、退出
│   │   ├── command.go         启动谁、带什么参数、在哪个目录
│   │   ├── process_windows.go Windows 差异（隐藏控制台窗口）
│   │   ├── process_other.go   其他平台的空实现
│   │   └── client_test.go     用真实子进程测协议行为
│   └── mockpi/server.go       假 Pi：服务端视角，不调用模型
├── frontend/
│   ├── src/bridge/pi.ts       唯一知道“生成绑定在哪”的文件
│   ├── src/app/AppShell.tsx   应用启动与三栏外壳
│   ├── src/hooks/usePiEvents.ts  唯一的事件监听器
│   ├── src/rpc/router.ts      协议事件到 Zustand 状态的翻译层
│   ├── src/stores/sessions.ts 按工作区持久化最后会话
│   ├── bindings/              wails3 生成的 TypeScript 绑定（调用 Go 用）
│   └── dist/                  Vite 构建产物（不提交，被 main.go embed）
└── scripts/build.ps1          一条命令完成构建
```

**分层的价值**：`internal/pi` 完全不知道有界面存在。所以同一套代码既能被
命令行跑（`cmd/rpc-demo`），也能被桌面程序跑，还能被测试直接跑。

## 2. 三条阅读路线

### 路线 A：只想搞懂协议 → 从命令行入口读

```text
cmd/rpc-demo/main.go  run()
   │  ① pi.Command(mode, cli, cwd)      决定启动谁
   ▼
internal/pi/command.go  Command()
   │  ② pi.Start(cmd, onTrace)          起进程 + 两个读取 goroutine
   ▼
internal/pi/client.go  Start() / read() / Request()
   │  ③ client.Request(ctx, "prompt", …)  发命令、等响应
   ▼
internal/mockpi/server.go  Serve()      对面是怎么回答的
```

建议顺序：先跑一遍 `go run ./cmd/rpc-demo`，对照输出读 `main.go`，
再读 `client.go`，最后读 `mockpi/server.go`。

`main.go` 里每读一行都问自己：这段代码对应上面输出的哪一行？

- `settled` 通道 ← 对应输出里的 `{"type":"agent_settled"}`
- `outputMu` ← 为什么需要？（因为两个读取 goroutine 会同时打印）
- `deadline` + `abort` ← 为什么超时要主动发 abort？（见协议文档第 6 节）

### 路线 B：想看桌面程序怎么把两边接起来 → 从上往下读

```text
frontend/src/main.tsx           挂载 React
   ▼
frontend/src/hooks/usePiEvents.ts  ① 监听 pi:event/pi:trace
   ▼
frontend/src/rpc/router.ts      ② 解释事件 ③ 更新 Zustand 状态
   │  piBridge.prompt(...)
   ▼
frontend/src/bridge/pi.ts       转发到生成的绑定
   │
   ▼
frontend/bindings/zeroa/piservice.ts   Call.ByID(3871518556, message)
   │  ── Wails 绑定（前端 → Go）──▶
   ▼
service.go  PiService.Prompt()  加超时 → 交给协议层
   │
   ▼
internal/pi/client.go           写出 stdin，等 response
   │  ── Pi 的事件 ──▶ onTrace
   ▼
main.go  service.onEvent = trace => Emit("pi:trace") + Emit("pi:event")
   │  ── Wails 事件（Go → 前端）──▶ 回到 usePiEvents 的监听器
```

**两个方向必须分清**（这是 Wails 架构里最重要的一条）：

| | 方向 | 用什么 | 谁发起 |
| --- | --- | --- | --- |
| Binding | 前端 → Go | `Call.ByID(方法ID, …)` | 前端主动调用 |
| Event | Go → 前端 | `app.Event.Emit` / `Events.On` | 后端主动通知 |

规则很简单：**请求用 Binding，通知用 Event。**
这与 Pi 协议自己的 command / event 划分天然一致。

### 路线 C：想看“怎么测协议” → 直接读测试

`internal/pi/client_test.go` 里的每种 `mode` 都模拟一类真实故障：

| mode | 模拟的场景 | 对应现实 |
| --- | --- | --- |
| `mock` | 正常一问一答 + 流式事件 | 一切顺利时 |
| `reverse` | 两条命令的响应倒序返回 | 并发命令、异步处理 |
| `hang` | 收下命令但永不回复 | 对端卡死 → 超时路径 |
| `exit` | 收下命令就退出 | 进程崩溃 → 退出路径 |
| `large` | 返回 100 KB 的记录 | 大消息、分帧边界 |

读测试时重点看**它断言了什么**，那就是这套实现承诺的行为。

## 3. 关键不变量（Invariants）

这些是代码里必须一直成立的条件；注释里也标了。改代码时如果破坏了它们，就会出问题。

| # | 不变量 | 破坏了会怎样 | 在哪守 |
| --- | --- | --- | --- |
| 1 | 一次写入 = 一整行 JSON + LF | 两行拼在一起，双方都解析失败 | `client.go` 的 `writeMu` |
| 2 | 先登记 pending，再写 stdin | 秒回的响应被丢弃，请求白等超时 | `Client.Request()` |
| 3 | 只有 `type=response` 才投递给等待者 | 事件被误当成某条命令的结果 | `Client.read()` |
| 4 | 先读完管道，再 `cmd.Wait()` | 丢掉最后几行（包括 `agent_settled`） | `Start()` 里的 `WaitGroup` |
| 5 | `writeMu` 只保护写，`mu` 只保护 pending | 死锁或数据竞争 | `Client` 字段注释 |
| 6 | 关 stdin 也要经过 `writeMu` | 半行 JSON 被截断 | `Client.Close()` |
| 7 | 连接状态由 `get_state` 能否作答决定 | 界面显示“已连接”但发不出消息 | `useAgent.ts` 的 `start()` |
| 8 | 列表用稳定 id 当 key | 日志从头部删除后界面错位 | `timeline.ts` 的 `nextId` |
| 9 | `message_end` 覆盖流式文本 | 界面文字与真实结果不一致 | `router.ts` + `timeline.ts` |
| 10 | 生成的绑定与 Service 方法同步 | 点按钮才报错，编译期发现不了 | `bindings_test.go` + `build.ps1` |

## 4. 数据在哪一层被“翻译”

同一条消息，在链路上换了六种形态。看懂这张表，调试时就知道该在哪里打断点。

```text
① 字节流             "{\"type\":\"message_upd…\n"
    │ bufio.Scanner 按 LF 切分
② 一行字符串         {"type":"message_update",…}
    │ json.Unmarshal
③ Response 结构      Type="message_update"
    │ onTrace 回调
④ Trace{Direction,Raw,Time}
    │ app.Event.Emit("pi:trace", …)   ← 跨语言边界（Go → JS）
⑤ JS 对象            event.data = {direction, raw, time}
    │ JSON.parse(raw) + 分支判断
⑥ React 状态         messages: [{id, role, text}]
    │ 渲染
⑦ DOM                <article>…</article>
```

**调试提示**：
- 界面没出字但日志里有 `text_delta` → 问题在 ⑤⑥（`router.ts` / `timeline.ts`）；
- 日志里根本没有 `text_delta` → 问题在 ①~④（协议层或 Pi 本身）；
- 界面显示“已连接”但发不出去 → 看第 3 节不变量 7。

## 5. 想改东西，该动哪里

| 需求 | 要改的地方 | 别忘了 |
| --- | --- | --- |
| 改 Pi 的启动参数（如打开工具） | `internal/pi/command.go` 的 `args` | 对照 `pi --help` 确认参数存在 |
| 加一条新命令（如 `set_model`） | `service.go` 加方法 → `bridge/pi.ts` 导出 → hook/组件调用 | 必须重跑 `scripts/build.ps1` 生成绑定，否则 `go test ./...` 会报错提示你 |
| 改超时时间 | `service.go` 的 `request()` | 超时≠取消，需要时补 `abort` |
| 让界面认识新事件 | `rpc/router.ts` + `rpc/types.ts` | 未知事件本来就应被安全忽略 |
| 改模拟器行为 | `internal/mockpi/server.go` | 同步更新 `client_test.go` 的事件顺序断言 |
| 让界面支持工具调用卡片 | 先看真实事件 `tool_execution_*` | 工具已经打开，直接发一条「建个文件」就能在观察器里看到 |
| 换掉 Wails（比如改 Electron） | 只需要替换 `main.go`/`service.go`/`frontend` | `internal/pi` 一行都不用动 —— 这就是分层的好处 |

## 6. 读代码时可以问自己的问题

1. `client.go` 里为什么要有两把锁？合成一把会怎样？
2. 如果去掉 `defer delete(c.pending, id)`，会发生什么？
3. `read()` 里 `ch <- envelope` 为什么要用带缓冲的通道？
4. `Close()` 为什么不能直接 `Process.Kill()` 了事？
5. 前端为什么只在 `App` 里注册一次监听器？注册多次会怎样？
6. `mockpi` 为什么必须先 `respond(...)` 再 `go func()` 发事件？反了会怎样？

想清楚这六个问题，Pi RPC 这一层基本就掌握了。
参考答案散落在源码注释里；也可以自己改坏它，看测试怎么失败。
