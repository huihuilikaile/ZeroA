# 03 · 实验手册

读代码不如改代码。下面每个实验都遵循同一个套路：
**改一处 → 观察现象 → 解释原理 → 用 Git 还原。**

> 还原命令统一是 `git checkout -- <文件>`（或 `git restore <文件>`）。
> 这正是把仓库放进 Git 的意义：随便试，不怕改坏。
>
> 本文的实验都在本机实跑验证过（Go 1.27.1 / Node 24 / Pi 1.0.0 / wails3 v3.0.0-beta.17），
> 下面写的“预期现象”就是实际观察到的输出。

---

## 实验 0 · 先跑通两条主线（不用改代码）

**目标**：先建立“输入什么、输出什么”的直觉。

```powershell
# ① 模拟模式：不需要模型、不需要 API Key
go run ./cmd/rpc-demo

# ② 真实模式：只查状态，不调用模型、不花钱
go run ./cmd/rpc-demo -mode real -check

# ③ 桌面界面
.\bin\zeroa.exe
```

**观察**：输出里第一条 `stdin` 是请求，第一条 `stdout` 是**同 id** 的响应，
接着才是不断到来的事件。桌面界面里右边栏就是这些原始行。

**要点**：模拟模式也是**真的子进程 + 真的管道**，只是对面不会调用模型。

## 实验 1 · 让流式变慢，看清“逐字到达”

**改**：`internal/mockpi/server.go`

```go
case <-time.After(18 * time.Millisecond):   // 改成 200 * time.Millisecond
```

**跑**：`go run ./cmd/rpc-demo`

**预期**：`text_delta` 从“刷屏”变成“一个字一个字往外蹦”，整段回复要几十秒。
桌面界面里能看到文字一段段出现，状态栏一直显示「正在生成」。

**原理**：界面上的流式效果完全由 `message_update / text_delta` 事件驱动，
和“模型有多快”没有关系。控制事件频率就控制了观感。

**⚠️ 不要改成 `0`**：那样 `select` 的 `ctx.Done()` 和 `time.After(0)` 会同时就绪，
Go 随机挑一个执行，`abort` 就变成抽签（有时生效、有时不生效）。
这是 `select` 语义的经典陷阱。

**还原**：`git checkout -- internal/mockpi/server.go`

## 实验 2 · 加一条自己的事件，验证“未知事件是安全的”

**目标**：确认客户端不会因为不认识某个事件就崩掉或状态错乱。

**改**：`internal/mockpi/server.go`，在 `emit(...agent_start...)` 后面加一行：

```go
emit(map[string]any{"type": "custom_progress", "percent": 42})
```

**跑**：`go run ./cmd/rpc-demo`

**预期**：
- 终端里多出这一行；
- 程序照常跑完，`agent_settled` 照常到达；
- 桌面界面的观察器里也能看到它，但对话区不受影响。

**原理**：客户端只按 `type` 分流：`response` 去配对，其他都当事件交给观察器。
**协议演进就是靠这个性质**——Pi 增加新事件时，老客户端不会坏。

**还原**：`git checkout -- internal/mockpi/server.go`

## 实验 3 · 亲手制造“两行 JSON 粘在一起”

**目标**：理解 `writeMu` 到底在保护什么。

**改**：`internal/pi/client.go` 的 `Request()`，把“一次写完一整行”拆成两次写入，
并临时去掉互斥。为了让交错**必然发生**，中间加一个 50ms 的窗口
（否则两次 Write 太快，可能碰巧不交错，现象不稳定）：

```go
	select {
	case <-c.done:
		err = errors.New("Pi 进程已退出")
	default:
		c.trace("stdin", string(data))
		_, err = c.stdin.Write(data)                  // 先写 JSON
		time.Sleep(50 * time.Millisecond)             // 制造交错窗口
		_, err = c.stdin.Write([]byte{'\n'})          // 再写换行
	}
	// 原来的写法：c.writeMu.Lock() … c.stdin.Write(append(data, '\n')) … c.writeMu.Unlock()
```

**跑**：`go test ./internal/... -run TestConcurrentResponsesMatchIDs -count=3`

**实测结果**：3 次全部失败，两条命令的内容被拼进同一行，
子进程解析不了，于是两个请求都等到超时：

```text
--- FAIL: TestConcurrentResponsesMatchIDs (3.02s)
    client_test.go: first 等待响应: context deadline exceeded
    client_test.go: second 等待响应: context deadline exceeded
```

**原理**：管道是字节流，`Write` 之间没有任何原子性保证。
`writeMu` 保证的是：**同一时刻只有一个完整的记录在写**，
从而让“一行 JSON + LF”在并发下依然成立。

**还原**：`git checkout -- internal/pi/client.go`

## 实验 4 · 破坏 id 配对，看测试怎么抓住你

**目标**：理解为什么必须靠 `id` 而不是到达顺序。

**改**：`internal/pi/client.go` 的 `read()`，把按 id 查表改成“任取一个”：

```go
// 原来的： ch := c.pending[envelope.ID]
var ch chan Response
for _, candidate := range c.pending {   // 随便挑一个等待者
    ch = candidate
    break
}
delete(c.pending, envelope.ID)
```

**跑**：`go test ./internal/... -run TestConcurrentResponsesMatchIDs -count=5`

**实测结果**：5 次全部失败，报错是这两种：

```text
client_test.go: response mismatch: want second, got first
client_test.go: first 等待响应: context deadline exceeded
```

第一个调用者拿到了本该给第二个的响应；而错配之后另一个请求再也等不到结果，直到超时。

**原理**：`reverse` 子进程故意让第二条命令的响应先回来。
如果客户端按“谁先到就交给谁”，两条命令的调用者会拿到彼此的结果 ——
这种 bug 在真实并发下极难排查，所以协议用 `id` 把它从根上消除。

**还原**：`git checkout -- internal/pi/client.go`

## 实验 5 · 中止：abort 与 timeout 的区别

**目标**：亲眼看到“超时 ≠ 停止”。

**改**两处让现象更明显：

```go
// internal/mockpi/server.go
case <-time.After(200 * time.Millisecond):   // 放慢回复

// cmd/rpc-demo/main.go
deadline, cancel := context.WithTimeout(ctx, 5*time.Second)  // 60s 改 5s
```

**跑**：`go run ./cmd/rpc-demo`

**实测输出**（末尾几行）：

```text
[21:39:04.411] stdout {"command":"abort","id":"req-3","success":true,"type":"response"}
[21:39:04.414] system process_exit
context deadline exceeded
exit status 1
```

而在它之前，stdin 方向确实出现了那条主动发出的中止命令：

```json
{"id":"req-3","type":"abort"}
```

**原理**：超时只是本地放弃等待，Pi 那边还在跑；代码在超时分支里**主动补了一条 abort**，
这才是让对面停下来的手段。真实产品里，这两件事必须分开设计。

**还原**：`git checkout -- internal/mockpi/server.go cmd/rpc-demo/main.go`

## 实验 6 · 对比真实 Pi：多出来的事件

**跑**：`go run ./cmd/rpc-demo -mode real -prompt "只回复四个字：链路正常"`

**预期**（真实 Pi 1.0.0 实测）：**事件骨架和模拟器是一样的**
（`agent_start`、`turn_start`、用户消息的 `message_start/end`、
`text_start/text_delta/text_end`、`turn_end`、`agent_end`、`agent_settled`）。
真正多出来的是这两类东西 —— 注意它们不是新事件，而是**字段和子类型**：

| 真实 Pi 多出来的 | 它到底是什么 | 本 Demo 是否处理 |
| --- | --- | --- |
| `usage`（内嵌 `cost`） | `message_update` / `message_end` 里的**顶层字段**：token 用量与花费 | 未展示，但日志里能看到 |
| `thinking_*` | `assistantMessageEvent.type` 的一种**子类型**（思考过程），开启思考时才出现 | 未渲染（只处理 `text_delta`） |

**原理**：模拟器覆盖的是**骨架**，不是全部字段。学协议要对着真实输出逐字段看，
而不是假设“模拟器就是协议的全部”。

**注意**：这一步会真的调用模型，产生少量费用。

## 实验 7 · 超时与崩溃路径（不用改代码）

**跑**：

```powershell
go test ./internal/... -run TestTimeoutAndExit -v
go test ./internal/... -v
```

**观察**：`hang` 子进程永不回复 → 走 ctx 超时分支；
`exit` 子进程收下命令就退出 → 走 done 通道分支。
两种情况下 `pending` 表都被清空（测试直接断言了这一点）。

**原理**：一个健壮的客户端必须能回答“等不到结果时会发生什么”，
而不是假设对面永远正常。

## 实验 8 · 大记录与分帧边界

**跑**：

```powershell
go test ./internal/... -run TestLargeUnicodeRecord -v
```

**改**：把 `internal/pi/client.go` 里的上限 `4*1024*1024` 改成 `64*1024`，
再跑一次。

**实测结果**：测试失败 —— 上限一降，那条 100 KB 的记录就过不去了：

```text
--- FAIL: TestLargeUnicodeRecord (0.03s)
FAIL
```

**原理**：任何流式协议都必须定义“单条消息能有多大”。
不设上限会吃光内存，设了上限就要定义超限后的行为 ——
这里的实现是：记录一条 `stdout_read_error` 的 system 记录，并结束进程。
想看那条记录长什么样，用命令行入口跑（它会把所有 trace 打印出来）；
`go test` 默认不打印 trace。

**还原**：`git checkout -- internal/pi/client.go`

## 实验 9 · 体验 `go:embed` 的构建约束

**改**（临时改名，不要删）：

```powershell
Rename-Item frontend\dist frontend\dist.bak
go build ./...
```

**实测结果**：编译失败，报错精确到行：

```text
main.go:17:12: pattern all:frontend/dist: no matching files found
```

而 `go test ./internal/...` 仍然通过（协议层不依赖前端产物）。
再执行：

```powershell
Rename-Item frontend\dist.bak frontend\dist
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/build.ps1   # 重新生成全部产物
```

**原理**：`//go:embed` 在**编译期**读取目录，目录不存在就直接编译失败。
所以新克隆的仓库必须先跑构建脚本 —— 这也是 README 里那句提醒的由来。

## 实验 10 · 让界面在子进程死亡后恢复

**目标**：验证连接状态不是“假绿灯”。

1. 打开桌面程序，点「启动 Pi」，此时是「已连接 · 空闲」；
2. 杀掉那个 mock 子进程。⚠️ 不能简单地 `Get-Process zeroa | Stop-Process`：
   mock 子进程和桌面程序**是同一个 exe**（带 `--mock-pi` 参数），
   按进程名杀会把父进程一起杀掉，窗口就没了。要按命令行区分：

   ```powershell
   Get-CimInstance Win32_Process -Filter "Name = 'zeroa.exe'" |
     Where-Object { $_.CommandLine -like '*--mock-pi*' } |
     ForEach-Object { Stop-Process -Id $_.ProcessId -Force }
   ```

3. 观察界面：应当回落到「未连接」，并且能直接再点「启动 Pi」恢复。

**原理**：子进程退出时 Go 侧发出一条 `process_exit` 的 system 记录，
前端据此把连接状态清掉；而「启动 Pi」内部先 `Stop()` 再 `Start()`，
所以**任何残留状态都能一键恢复**，不会卡在“请先关闭”。

## 实验记录建议

每做完一个实验，用一次提交记录下来：

```powershell
git add -A
git commit -m "exp: 把 mock 流式延迟改成 200ms，观察逐字渲染"
git checkout -- <改动的文件>   # 或保留改动，看个人习惯
```

把“实验分支”留下来，过几周回看时，能直接对比 `git diff` 前后的行为差异 ——
这是学习协议最快的方式之一。
