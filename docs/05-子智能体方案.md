# 05 · 子智能体方案（Go Supervisor + 后台委派）

这份文档把"主 Agent 派活给子 Agent、自己继续干活"这件事定下来：**做什么、为什么这么做、怎么落地、怎么验证**。
它是一份可以直接照着实现的方案，不是调研笔记。

---

## 0. 一句话概括

```text
一个子智能体 = 一个独立 Pi 进程，由 Go 管理；父 Agent 派活后立刻继续工作，
子 Agent 完成后由 Go 把归一化摘要投递回父会话。
```

**边界**：Pi 负责单 Agent 的 LLM↔工具循环；Go 负责 spawn / kill / 权限 / 预算 / 结果路由 / UI；React 只负责显示。
**第一版硬约束**：`depth ≤ 1`（子 Agent 不能再派子 Agent）。

---

## 1. 能不能做：四件基础件已经在手

| 需要的能力 | 现状 |
|---|---|
| 起一个独立 Pi 进程 | ✅ `pi.Command(opts)` + `pi.Start(cmd, onTrace)`，回调能拿到子进程每一行 JSONL |
| 按角色配置子 Agent | ✅ `compileRole` + `applyToOptions`（提示词 / 工具白名单 / 模型 / 技能 / 权限） |
| 往父会话注入消息 | ✅ RPC `follow_up`（回合结束后投递）与 `steer`（下一个检查点插话） |
| 权限与预算语义 | ✅ `permission.Engine` 四层交集 + TaskLoop 轮次/时长 |
| **Supervisor（登记 + 生命周期）** | ❌ 待做 |
| **delegate 桥（Go ↔ Pi 扩展）** | ❌ 待做 |
| **结果路由（归一 + 择时投递）** | ❌ 待做 |

> Pi 的 RPC **没有** spawn 原语（`rpc-commands.md` 里只有 `fork`/`clone` 这类会话级操作）。
> 所以"进程归 Go 管"不是妥协，而是唯一干净的位置——把生命周期交给扩展，就等于把权限、预算、kill、UI 全锁进那个进程里。

## 2. 调研结论：为什么不用现成扩展当核心

| 包 | 许可 | 量级 | 子进程模型 |
|---|---|---|---|
| `pi-subagents`（nicopreme） | MIT | 583K/月 | **前台 = 父进程内子会话**；后台 = detached runner |
| `pi-background-tasks`（ismailsaleekh） | ISC | 109K/月 | 一子一 Pi 进程 |
| `@tintinweb/pi-subagents` | MIT | v0.19.0 | 类似 pi-subagents |
| 官方示例（随 Pi 包发布） | 随 Pi | — | 一子一进程（`--mode json -p --no-session`） |

两条路线只有一条能实现我们的诉求：

| | A：进程内子会话 | B：一子一进程（**本方案**） |
|---|---|---|
| 隔离 | ❌ 子会话与父同进程，一个卡死全崩 | ✅ 独立进程、独立内存 |
| Go 能否单独 kill / 限额 / 观察 | ❌ 只能通过扩展内部 API | ✅ Go 就是进程的主人 |
| 单独配 model / tools / permission | 部分 | ✅ 启动参数天然支持 |
| 代价 | 省内存、流式顺滑 | 每子 ~100MB + 1–3s 启动 |

**结论**：不照搬它们的实现，但把它们踩过的坑抄过来。

### 从 `pi-subagents` 直接继承的 7 条设计

1. **能力上限是带外、会话级的**（`registerSubagentCapabilityCeiling` 那种），不放进模型可见的工具参数——模型无法讨价还价。
2. **工具懒激活**：先给一个小的 loader 工具，授权后再让完整 schema 出现在下一次请求里，避免中途加工具打破 provider 的 prompt cache。
3. **总量护栏**：把"活动并发"和"一次运行树累计起了多少子 Agent"分开算。
4. **模型可见结果要裁剪**：任务输出上限（它们 50KB/任务，我们先用 8KB），完整结果留在细节里。
5. **启动前 preflight**：起之前把"最终会用哪个模型、哪些工具、什么上下文"算出来给用户看——我们的 `ResolveRole` 编译预览已经是这个形状。
6. **宿主生命周期**：detached 子进程不随会话结束；判断存活要读 run 状态文件 + **记录 runner pid**，`lastUpdate` 不是心跳。我们的 Go 本来就是 pid 主人，天然占优，但要避免"界面空闲就回收进程"。
7. **观察面**：每个 run 一个状态 + 事件流 + FleetView，就是我们的 Agents 页与 All-Agents Timeline。

**不抄的**：官方示例把 spawn 错误吞成 `"(no output)"`（issue #8129，已关闭）——子进程起不来必须报出原因。

## 3. 端到端数据流

```text
父 Pi ──delegate_task(role, task)──▶ delegate-task 扩展（Node，~60 行）
                                          │ HTTP 127.0.0.1:<随机端口>
                                          │ x-delegate-token: <每会话随机>
                                          ▼
                                    Go Supervisor
                        ├─ 闸门① 会话授权 ∩ 角色策略（模型改不了）
                        ├─ 闸门② 审计代理条件（读过附件 + ≥1 轮）
                        ├─ 闸门③ 预算 / 并发 / 深度
                        ├─ spawn：子 Pi 进程（独立 session-dir / cwd / model / tools）
                        └─ 立刻返回 {agentId:"agent-2", status:"running"}
                                          │
   父收到"已派出" → **继续解题**             │ 子进程在后台跑
                                          ▼
                          子 agent_settled → 归一 SubAgentResult
                                          ▼
                          ResultRouter：合并窗口 + 择时 → follow_up 注入父会话
```

## 4. 核心概念

```text
RoleDefinition   （模板：提示词 / 工具 / 模型 / 技能 / 权限 / 委派策略）
      ↓
AgentDefinition  （这一次要用的具体配置）
      ↓
AgentInstance    （正在跑的实例：ID / 父ID / 状态 / 进程 / 预算）
      ↓
Pi RPC Process   （一个实例 = 一个进程）
```

同一个角色可以实例化多次：

```text
AgentInstance #A  Role = CTF-Reverse  Task = 分析 challenge.exe 的核心验证
AgentInstance #B  Role = CTF-Reverse  Task = 从算法角度独立分析同一个文件
```

它们是两个完全独立的 Agent，互不知道对方的上下文。

### 状态机

```text
Created → Starting → Running → Completed
                        │   ↘ Failed
                        │   ↘ Cancelled（超时/主动停）
                        └──→ Killed（强杀）
```

### SubAgentResult（唯一回流给父的东西）

```go
type SubAgentResult struct {
    AgentID   string
    RoleID    string
    Status    string        // completed | failed | cancelled | killed | timeout
    Summary   string        // 2–5K tokens，硬上限 8KB
    Findings  []Finding     // 结构化结论
    Artifacts []ArtifactRef
    Usage     UsageStats    // turns / input / output / cacheRead / cost
    SessionDir string       // 完整过程在这里，可查看但不回流
}
```

**绝不把子会话完整塞回父上下文**——那是"多智能体"最常见的翻车方式。

## 5. 模块划分（Go）

```text
internal/agents/
  supervisor.go   实例登记、spawn/kill/取消、并发与深度闸门
  launch.go       SpawnRequest → pi.Options（复用 compileRole）
  result.go       子进程 JSONL → SubAgentResult（8KB 上限 + 超限指路）
  router.go       结果合并与投递时机（父忙/闲、父已结束）
  budget.go       会话预算（个数/并发/时长/token）
delegation_bridge.go   HTTP 控制口（package main）
agent_tools_api.go     给 Wails 前端的绑定：agents_list / agent_kill / delegation_grant
```

核心接口：

```go
type Supervisor interface {
    Spawn(req SpawnRequest) (*Instance, error)   // 立刻返回，不等结果
    Kill(id, reason string) error
    CancelChildren(parentID, reason string) int  // 父 abort 时用
    Get(id string) (*Instance, bool)
    Children(parentID string) []*Instance
}

type SpawnRequest struct {
    ParentID     string
    RoleID       string
    Task         string
    ParentDepth  int           // 0 = 主 Agent；用于执行 depth ≤ 1
    MaxDuration  time.Duration
    AllowedRoles []string      // 会话授权 ∩ 角色策略的产物
}
```

## 6. 桥：为什么是 HTTP + env token

扩展跑在 Node 里，HTTP 是两边唯一都天然支持的通道。

- 端口**随机**、token**每会话随机**、只绑 **127.0.0.1**；
- token **不落盘**：`pi.Command` 已经在拼 `env`（`PI_CODING_AGENT_DIR` 那行），加一个 `Options.ExtraEnv` 注入 `PI_GUI_DELEGATE_URL` / `PI_GUI_DELEGATE_TOKEN`；
- 扩展只做三件事：读 env、POST、把返回文本当工具结果。**它不 spawn、不 kill、不判权限、不管预算。**

```ts
export default function (pi: ExtensionAPI) {
  pi.registerTool({
    name: "delegate_task",
    description: "把一项独立任务交给子 Agent（独立进程/独立上下文）后台执行；完成后结果自动回到本会话。",
    parameters: Type.Object({ role: Type.String(), task: Type.String() }),
    async execute(_id, params) {
      const res = await fetch(`${process.env.PI_GUI_DELEGATE_URL}/delegate`, {
        method: "POST",
        headers: { "content-type": "application/json", "x-delegate-token": process.env.PI_GUI_DELEGATE_TOKEN! },
        body: JSON.stringify(params),
      });
      const data = await res.json();
      return { content: [{ type: "text", text: data.message }] };
    },
  });
}
```

### 工具契约（模型看到什么）

`delegate_task({role, task})` **立即**返回：

```
已派出子智能体 agent-2（角色 research-web），它在后台查资料。
完成后结果会自动出现在你的会话里，你现在可以继续解题。
```

配套 `delegation_list()` 查状态。角色声明 `mode: "blocking"` 时工具才等结果。

## 7. 委派生命周期

```text
① 用户选角色 → 弹窗勾选本次会话允许的子 Agent（见第 9 节）
② 父审计题目/附件（Go 观察工具调用，闸门②）
③ 父调 delegate_task(role, task)
④ Go 三道闸门 → spawn 子进程 → 立刻返回句柄
⑤ 父继续解题（时间线出现"委派卡片"，可点开看子 Agent 的实时输出）
⑥ 子 agent_settled → 抽最终文本 + usage → 归一（8KB 上限）
⑦ ResultRouter 合并 + 择时 → follow_up 注入父会话
⑧ 时间线出现"研究简报卡片"；Agents 页可看子 Agent 完整对话
```

### 审计闸门（诚实版）

| 层 | 内容 | 强度 |
|---|---|---|
| 硬（Go 可判定） | 父会话至少一次针对附件/工作区的 `read`/`bash` 调用；至少 1 轮；未超预算 | 强制 |
| 软（提示词） | 角色提示词要求"先审计题目与附件，再决定是否委派" | 约束模型，不保证 |

**明确不做**：假装能判定"审计完成"这个语义。事件总线看得到工具调用，看不到语义。

## 8. 结果路由（最容易做错的一段）

| 情况 | 规则 | 理由 |
|---|---|---|
| 多个子 Agent 短时间内完成 | **1.5s 合并窗口**合成一条消息 | 否则父上下文被碎片冲爆 |
| 父正在跑回合 | 等 `agent_settled` 再投（默认）；`deliverOn: checkpoint` 时用 steer 立刻插 | 解题中途插半成品研究会污染推理 |
| 父空闲 | `follow_up` 唤醒 | 不然成果没人看 |
| 父已给出最终答案、用户也没再说话 | **不唤醒**，只进时间线 + 未读角标 | 避免僵尸回合 |
| 子失败 / 超时 / 被杀 | 同样投递，状态行写明原因 + stderr 摘要 | 见第 2 节"不抄的" |

投递格式固定（父模型好解析）：

```
[子智能体结果] agent-2 · ctf-recon · completed · 12.3s · 3.1k tokens
<2–5K tokens 的摘要>
（完整过程：<session dir>）
```

## 9. 权限、授权与继承

### 子权限只能收紧

```text
Child = Parent ∩ Role ∩ 全局 ∩ 会话授权
```

父禁网络 → 子角色即使写 `allow` 也拿不到。这条由 `permission.Engine` 加一层 Parent 实现。

### 会话授权弹窗（用户可点版本的能力上限）

选角色后弹出（仅当角色声明了 `delegation`）：

```
这个角色可以派子 Agent。本次会话允许：
  [x] 资料检索 ctf-recon     最多 [2]
  [x] 结论复核 ctf-verify    最多 [1]
  [x] 路线探索 ctf-route     最多 [2]
  继承：skills [全部▾]  MCP [只读抓取▾]  模型 [各自角色自己的▾]
  预算：子 Agent 总计 3 个 / 并发 2 / 单个 10 分钟
```

存成 `sessionDelegation{allowedRoles, maxChildren, maxParallel, budget, inherit, approvedAt}`，与现有"临时授权"同一处落盘；
**每次 spawn 校验 `角色策略 ∩ 会话授权`**，因为不在工具参数里，模型无法绕过。

### 继承矩阵与实现代价

| 继承项 | 能否真隔离 | 做法 |
|---|---|---|
| skills | ✅ | 子取"父编译结果 ∩ 子角色声明"，`--skill` 列表现成 |
| tools | ✅ | `--tools` 白名单 |
| model / thinking | ✅ | `--model provider/id:thinking` |
| permissions | ✅（只能收紧） | Engine 加 Parent 层 |
| **MCP** | ⚠️ 需 per-child agent dir | Pi 的 MCP 只认 `<agentDir>/mcp.json`，没有按进程过滤的开关 |
| **extensions** | ⚠️ 同上 | packages 来自全局 settings.json |

细粒度继承的唯一干净做法：给每个子 Agent 一份**独立 agent dir**——junction 链 `npm/`、`skills/`，自写过滤后的 `mcp.json` + `settings.json`，`PI_CODING_AGENT_DIR` 指过去。
**排在 S5.5**；在那之前弹窗里这两项只能写"继承全部 / 完全不用"，不给假的细粒度。

## 10. 预算与并发

| 参数 | 默认 | 说明 |
|---|---|---|
| `maxDepth` | 1 | 子不能再派子 |
| `maxChildren` | 3 / 会话 | 累计，不是并发 |
| `maxParallel` | 2 | 同时运行 |
| `childBudget.maxDurationSeconds` | 600 | 单个子 Agent 硬上限 |
| `childBudget.maxTokens` | 120000 | 超出即停 |

内存：每子一个 Node 进程 ~100MB；Agents 页显示占用与实时用量。

## 11. CTF 落地设计

### 为什么 CTF 特别吃子 Agent

1. **上下文才是稀缺资源**：`objdump -d`、`strings`、volatility 转储、几十 MB 日志会把父的窗口吃光，然后它开始忘掉自己的假设。子 Agent 各自一份窗口，只回摘要。
2. **答案是可验证的（flag）**：不需要投票共识，需要**覆盖不同的假设**。同模型重复采样会在同一个错误假设上失败同样的次数。
3. **侧任务天然独立**：查 wp/资料、试多条解法、跑爆破/符号求解——都是独立侧任务，交给子 Agent 不打断主线。

### 子 Agent 清单

| 子角色 | 模型 | 工具/权限 | 干什么 | 何时派 |
|---|---|---|---|---|
| `ctf-recon` | 快而便宜 | web.search + 只读 | 查 wp / 资料 / 工具用法 | 审计完题目**立刻**派，父继续解题 |
| `ctf-verify` | **与父不同** | 只读 + bash | 反驳候选 flag / 复核关键推理 | 拿到 flag 或关键结论时，几乎无脑开 |
| `ctf-route` | 强推理 | bash + 只读，独立 angle | 并行试不同解法 | 卡住或发现多解法时，弹窗确认 |
| 父（supervisor） | 最强 | 唯一有写权限 | 判断、整合、写最终 solver | — |

### 决策规则

| 情形 | 决定 |
|---|---|
| 预估 > 2–3 分钟，或会产生大量工具输出 | 派 |
| 与主线独立（查资料、试另一条路） | 派 |
| 线性链条的一环（定位判断 → 逆算法 → 写脚本） | 自己干，拆开会丢线索 |
| 混合题的三条独立线索 | 并行派 |
| 有多个互斥假设要同时推进 | 派 route 探索（不同 angle） |
| 5 分钟能做完的小题 | 自己干（spawn 要 1–3s + ~100MB） |

### 多模型的正确用法

| 用法 | 值不值 | 说明 |
|---|---|---|
| 按方向配模型（每个子 Agent 一个模型） | ✅ 强烈建议 | crypto 要强推理、web/pwn 要代码+工具、recon 要快而便宜 |
| 卡住 >N 轮时换个模型"我在哪错了" | ✅ 值 | 同模型卡住后会一直卡住 |
| 用另一个模型**反驳**候选 flag | ✅ 便宜且高价值 | 抓巧合的 flag / 幻觉 |
| 同任务并行多模型"投票选答案" | ❌ 默认不要 | 错误相关 + N 倍成本；CTF 缺的是独立假设，不是共识 |

### 成本账（量级估算）

| 类型 | token 量级 | 触发建议 |
|---|---|---|
| recon | 3–8k | 默认自动 |
| verify | 5–10k | 默认自动 |
| route 探索 | 20–50k × N | 弹窗确认，并发 ≤2 |

回本逻辑：子 Agent 让父少走 5 轮错误尝试（每轮约 8k）就回本。

### 可测量

flag 可验证 → 每次委派记一条：**父的下一步是否改变 / 子结论是否进入最终答案**。跑十几道题就有数据调默认值。

## 14. 验证方案

**零 token 单测**（用现有假 CLI 夹具）：

- 起子进程 → 断言拿到 result / usage / 终态；
- `depth > 1`、`maxChildren`、`maxParallel` 各自被拒；
- `follow_up` 的内容与格式正确；
- 父忙时不投、`agent_settled` 后投、父已结束不唤醒；
- 子进程起不来（错路径）→ 失败原因包含 stderr 摘要，不是 `"(no output)"`。

**少量 token 集成**：父派一个 `ctf-recon` 子 Agent，观察 ①工具立即返回 ②父继续输出 ③子完成后父收到结果消息。

**边界**：子超时、子无输出、父 abort、父先结束、同一附件被父子同时读（只读不冲突）。

## 15. 风险与不做清单

| 风险 | 处理 |
|---|---|
| 子进程内存（每 Node ~100MB） | `maxParallel` 默认 2，Agents 页显示占用 |
| token 泄漏面 | 端口随机 + 每会话换 token + 只绑 127.0.0.1；token 不进日志、不落盘 |
| 子 Agent 写坏工作区 | 默认只读；要写的角色限定 `.agents/<id>/`，父决定是否采纳 |
| abort 后进程残留 | 父 abort → 子 abort → 3s → kill，断言 0 残留 |
| 结果把父上下文撑爆 | 8KB 硬上限，超限只给路径 |
| 委派变成"甩锅" | 审计闸门 + 决策规则（第 11 节）+ 可测量（子结论是否进入最终答案） |

**第一版不做**：`depth > 1` 递归 spawn · Blackboard / Agent 互聊 · Planner 自动拆任务 · 无鉴权的 localhost 控制口 · 让扩展自己 spawn 进程。
