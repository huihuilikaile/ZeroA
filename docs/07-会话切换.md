# 07 · 会话切换（为什么"点一下就切"会把正在跑的回合弄没）

这份文档记录用户报的两个现象、根因、这次的修法，以及**还没做的那一步（架构级）**。
和 `05/06` 一样，它是可验证的：每条结论后面都有落点。

---

## 0. 一句话

```text
Pi 只有"一个常驻进程"，switch_session 是"让这个进程换一份会话文件继续干活"。
在回合运行中切，就等于把这轮从它所属的会话里抽走 —— 所以默认改为"排队等它跑完"，
要立刻切必须走显式的"中断并切换"；同时把切换的等待时间从"扫盘 + 全量重建"压下来。
```

---

## 1. 现象与根因

| 现象 | 直接原因 | 更深一层 |
|---|---|---|
| 侧栏点另一个会话，**正在跑的那一轮直接结束** | Go 侧对常驻 Pi 发 `switch_session`（`sessions.go` 的 `performLoadSession`） | Pi 的进程模型是"一个进程 + 当前会话文件"。`switch_session` 让进程改绑到另一份文件（`rpc-mode.js:474` → `runtimeHost.switchSession` → `rebindSession`），进行中的回合没有归宿 |
| 改名/删除**也会**打断 | `RenameSession` 对非当前会话要"切过去 → 改名 → 切回来"（两次 switch）；`DeleteSession` 删当前会话前要 `new_session` | 同一根因的另外两个入口，之前完全没设防 |
| 切换**慢** | ① `scanAllSessions` 每次刷新都遍历会话目录、逐个文件读开头 + 末尾 64KB；② 切换要三个串行 RPC（`switch_session` → `get_messages` → `get_state`），其中 `get_messages` 可能返回 MB 级 JSON；③ 前端拿到后重建整条时间线并**渲染全部**历史条目 | 前两条是"必须做的 IO"，第三条是纯粹的自找 |

> 损失为什么不可接受：被掐掉的那一轮，模型已经烧掉的 token、已经执行过的工具
> （可能改了磁盘、跑了扫描）都白费，而且**没有任何提示**——用户以为只是换了个视图。

## 2. 参考项目对照（`E:\2026PlayLearn\CTFAgentPi\CTFAgentPi`）

调研结论（只读，证据见该仓库文件:行）：

| 问题 | CTFAgentPi 的做法 | 我们能抄吗 |
|---|---|---|
| 切换会话 | **没有 switch 这个动作**。一个任务 = 一个沙箱容器 = 一个独立 Pi 进程，切换只是前端 `setSelectedTaskID`（`App.tsx:987`），Go 侧零 RPC | 不抄（要拆进程，见 §5） |
| 正在跑的回合 | 不受任何影响。要停只能显式 `Pause`/`Abort`，且 `Abort` 只发 `{"type":"abort"}` **不杀进程**（`internal/sandbox/manager.go:1134`） | **抄语义**：中断是显式动作、且不销毁会话 |
| 历史加载 | SQLite `task_events` 表 + `(task_id, sequence)` 唯一索引 + 游标分页（单批上限 5000） | 不抄（我们要迁存储，收益不匹配） |
| 切换后的渲染 | **LRU 缓存最近 3 个任务的事件**，effect 里**同步**把缓存灌进 state，再异步补增量（`useTaskEvents.ts:9,151`）；snapshot 带 taskId 防竞态（`:12-16`） | **抄**（这是"切换不白屏"的关键一行） |
| 长会话 | 全量拉、无 virtual list、无首屏截断 | 不抄（它是反面样本） |

**一句话**：它快不是因为它优化得好，而是因为"切换不需要 IO"。它的两个机制（LRU 快照、abort 不杀进程）可以独立生效，但根治要靠拆进程。

## 3. 修复一：排队切换（默认不打断）

### 3.1 状态机

```text
用户点会话 ──► LoadSession(path)
                 │
                 ├─ 没有回合在跑 ──► performLoadSession：切 + 取消息 + 取状态 ──► 前端按新会话重建
                 │
                 └─ 有回合在跑 ────► 只记住 pendingSessionPath，返回 {deferred:true}
                                      │
                                      └─ agent_settled ──► handleSettled
                                                            │
                                            ┌───────────────┴────────────────┐
                                    循环要再来一轮                  循环不再续跑
                                 （replan/summarize）                    │
                                            │                            ▼
                                     不切，继续排队            runPendingSessionSwitch
                                                              （goroutine：切+取消息+取状态）
                                                                      │
                                                              pi:session 事件推给前端
```

### 3.2 落点

| 位置 | 做什么 |
|---|---|
| `sessions.go` `LoadSession` | `turnRunning()` 为真 → 记 `pendingSessionPath` + 返回 `{deferred:true, path}`，**不发 switch_session** |
| `sessions.go` `LoadSessionForce` | 显式"中断并切换"：先 `abort`，再 `waitTurnIdle(3s)` 等收尾事件让出来，然后照常切换 |
| `sessions.go` `performLoadSession` | 真正干活的路径（切 → 取消息 → 取状态 → 记记忆），带分步耗时日志 |
| `service.go` `handleSettled` | 循环不再续跑时 → `go runPendingSessionSwitch()` |
| `service.go` `turnRunning()` | `parentBusy`（事件流）**或** `runningWork`（前端上报）——任一说在跑就当在跑 |
| `main.go` | 注入 `onSessionSwitch`，发 `pi:session` 事件 |

### 3.3 三个必须写下来的坑

1. **必须开 goroutine**：`handleSettled` 跑在 `internal/pi` 的**读取 goroutine** 上，
   而切换要发请求并等响应——由这条 goroutine 自己等自己会**直接死锁**。
   （同样原因，任务循环的 `sendLoopMessage` 本来也是 `go func()` 出去的。）
2. **循环要继续时不切**：角色配了 loop（卡住→replan / 到限→summarize）时，
   那一轮结束不等于任务结束；此时切等于把循环的下一轮掐掉，与"排队等它跑完"的承诺相反。
3. **强制切换要先等收尾**：`abort` 之后 Pi 还会发 `message_end/turn_end/agent_settled`，
   不等就切过去，这些**属于旧会话**的事件会被界面追加到新会话的时间线上（串台）。
   等不到（超时 3 秒）也照常切——用户点的就是"立即"。

### 3.4 顺带堵住的同类入口

- `RenameSession`：回合运行中直接拒绝（"当前回合正在运行，等它结束再改名"）。
- `DeleteSession`：删**当前**会话时才拒绝（非当前会话的删除不碰进程，允许）。

## 4. 修复二：把等待时间压下来

| 层 | 改动 | 为什么有效 |
|---|---|---|
| Go | `session_index.go`：会话索引缓存，按 **mtime + size** 判断文件是否变化，只有变了的才重新解析 | 列表刷新发生在每次新建/删除/改名/切工作区；原本每个文件都要读开头 + 末尾 64KB |
| Go | `load_session` 增加分步耗时日志（`switch_ms` / `messages_ms` / `state_ms` / `total_ms`） | "切换慢"要能一眼看出慢在哪一段，否则只能猜 |
| 前端 | **LRU 快照（3 条）+ 同步恢复**：命中缓存时先把内容画出来，再发 RPC 刷新 | 抄参考项目验证过的做法：用户点下去立刻有内容，而不是盯着空白等三个 RPC |
| 前端 | **竞态守卫**：只有最后一次发起的 open 允许写状态 | 快速连点两个会话时，先返回的旧结果不能覆盖后点的 |
| 前端 | 长会话**窗口化渲染**：默认只渲染最后 150 条，顶部「显示更早的 N 条」 | 时间线是纯 DOM 渲染（无虚拟列表），一条含 Markdown/工具卡片，几百条就是几百个组件 |
| 前端 | 待切换横幅 + 侧栏「待切换」徽标 | 排队是"看不见的状态"，不显示出来用户会以为点击没生效 |

> 关于 `get_messages`：**不改成自己解析 JSONL**。会话文件的分支/压缩语义由 Pi 实现，
> 自己解析一份等于把 Pi 的语义复制过来，迟早漂移。这一层保持"问 Pi 要"。

### 4.1 实测数字（2026-10-07，本机 Windows）

用 `switch_perf_manual_test.go` 里的两个手工探针测得（默认跳过，命令见文件头注释）：

| 测量项 | 条件 | 结果 |
|---|---|---|
| 会话列表扫描 | 78 个会话文件 / 4.0 MB | 全量解析 **49.0 ms** → 索引缓存命中 **4.6 ms**（约 **10×**） |
| `load_session`（小会话，payload 68 KB） | 真实 Pi，**不**加载扩展 | **45 ms** |
| `load_session`（大会话，payload 1.38 MB） | 真实 Pi，**不**加载扩展 | **73 ms** |
| `load_session`（同一份 1.38 MB 会话） | 真实 Pi，**按应用默认加载扩展/技能** | 首次 **247 ms**，二次 **128 ms** |
| 首次 `get_state`（启动成本） | 同上 | 808 ms（不加载扩展时 279 ms） |

**结论（决定了优化方向）**：RPC 侧不是瓶颈——**1.38 MB 的会话切一次也只要 73~250 ms**。
用户感觉到的"慢"来自前端：把 1.38 MB 的 JSON 解析成时间线、再把几百个条目（每条含 Markdown
与工具卡片）全部挂到 DOM 上。所以这一轮的优化重点放在前端（LRU 快照 + 窗口化渲染），
而不是继续压 Go 侧。

## 5. 还没做：一会话一进程（根治方案）

参考项目的做法是把约束取消掉：**一个会话一个 Pi 进程**，切换退化成纯视图操作，
两个问题同时消失。代价与要点：

| 项 | 说明 |
|---|---|
| 收益 | 切换完全不动进程；两个会话可以**同时**跑；`abort` 只影响一个会话 |
| 成本 | 每进程 ~100MB 级内存；需要在 Go 侧管理 N 个进程的生命周期（现在 `Supervisor` 已经会管子智能体进程，有先例） |
| 必须配套 | 全局并发上限 + FIFO 队列（否则用户开十个会话就是十个模型同时在烧 token）；每个进程的 `delegate_bridge` 端口/令牌要独立（现在是"每进程一个桥"）；"哪个进程是当前会话"要成为显式状态 |
| 不建议一次做完 | 先做本轮的排队 + 缓存（收益立刻可见），把"同时跑两个会话"作为独立需求再评估 |

### 6.3 端到端抓到的 bug（已修）

**现象**：点横幅上的「立即切换」，日志里又出现一次 `load_session deferred`，按钮看起来毫无反应。

**根因**：`LoadSessionForce` 在 `abort` 并等 `agent_settled` 之后，仍然调用了 `LoadSession`；
而 `LoadSession` 会按 `turnRunning()` 再判一次忙——`turnRunning()` 里含**前端上报**的 `runningWork`，
此刻前端还没处理完中止后的事件，`runningWork` 仍是 true，于是刚中断完又被排进队列。

**修法**：强制路径直接调 `performLoadSession`（中断 + 等协议层收尾已经是"显式中断"的全部代价），
并把工具缓存失效下沉到 `performLoadSession`，保证排队/强制两条路径都覆盖。
配套回归用例：`TestLoadSessionForceBypassesReportedRunning`（修复前会红）。

**教训**：`turnRunning()` 用"后端事件 + 前端上报"取或是**故意的保守**（宁可多等也别切断用户的工作），
但保守判断只适用于"要不要排队"，不能用在"用户已经明确要求中断"之后——
这两处的判据必须分开，混用就会出现"按钮点了没反应"。

## 7. 第二次排查（用户反馈"还是会被中断"）

上一版的"排队"逻辑是对的，但**真正打断回合的不是 `switch_session`**。用户日志给出了答案。

### 7.1 真凶：「会话带回角色」在重启进程

日志上，用户每点一次会话，中间都夹着：

```text
13:10:26.681 set_active_role workspace=… role=role-b
13:10:26.689 delegate_bridge_stopped          ← 进程被停掉重建
13:10:26.711 delegate_bridge_started
```

原因在 `Sidebar.tsx` 的点会话处理：一条会话记着它当初属于哪个角色，而**角色只能进启动参数**
（Pi 没有 `set_system_prompt`），所以"回到这条会话"= `switchRole()` = `start()` = **stop + start**。
于是"点一下会话"这个在用户看来跟切视图没区别的动作，把正在跑的那一轮连进程一起杀了。

手动从角色菜单切时有个确认框兜着（`RoleBadge`），而这条路径**一个确认都没有**。

**修法**：回合在跑时改成明确的二选一（`Sidebar.tsx`）——

| 选择 | 行为 |
|---|---|
| 「中断回合并切换角色」（危险按钮） | 走原逻辑：切角色 → 重启 → 打开目标会话 |
| 「取消」＝ 只打开会话 | **不切角色**，照样把那条会话打开（历史照看），回合不受影响 |

E2E（隔离安装 + 两条不同角色的会话 + mock 慢速回合）：

| 步骤 | 观测 | 结果 |
|---|---|---|
| 回合运行中点「属于角色B」的会话 | 弹出确认框；**回合仍在跑**；日志里**没有** `set_active_role` / `delegate_bridge_stopped` | ✅ |
| 选「取消」 | 依旧没有重启进程，回合继续 | ✅ |
| 选「中断回合并切换角色」 | `set_active_role role=role-b` → 重启 → 打开目标会话 | ✅ |

### 7.2 同时修掉一个把问题放大的 bug：忙碌标记漏气

`parentBusy`（后端事件流）与 `runningWork`（前端上报）**只在 `agent_settled` 时被清**。
但"回合结束"不只有这一种表达：

- 进程被停掉/重启（切角色、改设置、换工作区）；
- 进程自己退出（崩溃、被杀）；
- 会话真的切过去了（新会话上不可能有回合在跑）。

这三条路上都没有 `agent_settled`，于是标记永远是 true → **之后每一次点会话都被排队等一个
永远不会结束的回合**，唯一出路是「立即切换」——而那个才是真的打断。用户日志正是这样：
连续 4 次 `load_session deferred` 夹着 2 次 `load_session_force_idle_timeout`。

**修法**：新增 `clearTurnState(reason)`，在三处调用（`process_exit` / `Start` 拿到新进程 / `Stop` /
`performLoadSession` 切换完成），并在 deferral 日志里把**两个来源分开记**
（`parent_busy=%v frontend_work=%v`）——只写一句 `turn_running` 的话，事后无法判断是谁在说谎。

回归用例（`session_busy_leak_test.go`）：进程退出后切换不再被排队、Stop 清标记、切换完成清标记、
Start 路径的接线、诊断日志。

### 7.3 最终修法（已落地）：一进程一会话

用户的原话是"每个会话都是独立的 pi 进程，切换会话怎么会中断？"——
当时**实现不是这样**：主会话只有一个 Pi 进程（`PiService.client` 单字段），
启动只带 `--session-dir`，切换靠 `switch_session` 让这个进程改绑（见 §1）。
"一个进程一个"的是**子智能体**（`internal/agents`），两件事容易记混。

现在改成了真的一进程一会话（`session_runtime.go`）：

| 行为 | 旧（单进程 + 排队） | 新（一进程一会话） |
|---|---|---|
| 点另一条会话 | 排队等回合结束（横幅 + 「立即切换」） | **立刻切**：换的是"跟哪个进程说话" |
| 正在跑的回合 | 被排队保护，靠忙碌标记判断（标记一错就"点了没反应"） | **根本不碰它**：不向正在干活的进程发 `switch_session`/`new_session`/`abort` |
| 切回已开过的会话 | 重新 `switch_session` + 搬 `get_messages` 历史 | **复用原进程**，只回一个 `get_state`（不重载历史） |
| 后台会话的输出 | 不可能有（进程只有一个会话） | 留在**它自己的**时间线里，切回去才呈现 |
| 忙碌状态 | 一个全局布尔（多进程下必然出错） | **每条会话一份**（`sessionRuntime.busy`，由它自己的事件维护） |
| 切工作区 | 停进程再按新目录启动 = 杀掉别处正在跑的活 | 只是换"当前会话"，别处的进程照跑 |
| 改名/删除后台会话 | 要"切过去再切回来"，回合运行中只能拒绝 | 在**目标会话自己的进程**里做（没开着就起个临时进程，做完就关） |
| 进程数 | 1 | 上限 6 + 空闲 15 分钟回收（只回收"不在跑、也不是当前会话"的） |
| 授权门禁 | 只在 `Start()` | 每次创建进程都过一遍（`startRuntime`，否则多开会话就绕过授权） |
