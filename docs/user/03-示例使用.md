# ZeroA · 示例使用

照着做就能跑通的例子。每个例子都写清**前提 → 提示词（可直接复制）→ 你会看到什么**。

> 通用前置：`设置 → 模型`已填密钥；左栏选好工作区；输入框左下角选好角色。

---

## 例 0 · 最小闭环：30 秒确认"它真的能干活"

**前提**：任意角色。

**输入**

```
用 bash 执行 uname -s 和 python -c "print(6*7)"，把输出原样贴给我。
```

**你会看到**

```
bash · uname -s; command -v python; python -c "print(6*7)"        575ms
  MINGW64_NT-10.0-26200
  42
```

- 工具卡片点开就是**命令 + 原始输出 + 耗时**，出错会显示退出码（例如 `退出码 127`）。
- 如果它回答"我没有 bash 工具"：角色的工具白名单里没给 bash（角色页 → Pi 工具）。

**顺手确认工具清单**（排查"工具到底有没有加载"最直接的一招）：

```
把你当前可用的工具名逐个列出来（只要名字，每行一个，用英文原名，不要解释）。
```

典型输出会包含：`read bash edit write` + 扩展工具（`delegate_task` `mcp` `web_search` …）。

## 例 1 · 逆向 ELF：让 IDA 变成模型的工具

**前提**：IDA 里装了 MCP 插件（打开数据库后自动起服务，`127.0.0.1:13391`）；`bin/.pi/mcp.json` 里有：

```jsonc
"ida": { "url": "http://127.0.0.1:13391/mcp" }
```

**在 IDA 里**：打开目标（例如 `main.exe.i64`）。

**给模型的第一句**（先让它自己摸清地形，别一上来就要答案）：

```
用 mcp 里的 ida 工具做侦察：列出函数（只看数量最多的前 20 个）、
列出导入表里和输入输出/加密相关的符号，然后告诉我"最值得先看的三个函数"和理由。
```

**接着指定方向**（把 IDA 的调用链串起来）：

```
对 sub_401000 做三件事：1) 反编译；2) 列出谁调用了它（xrefs_to）；
3) 找出它内部引用的字符串。把结果整理成"输入 → 变换 → 输出"的表格。
```

**期望行为**：模型会依次调 `list_funcs` / `imports` / `decompile` / `xrefs_to` / `search_text` 这类工具，每个调用在对话里都是一张卡片，你能核对它读的是不是真的那块代码。

**写 exploit 时**：

```
基于上面的分析写一个 Python exploit，用 pwntools，本地跑通再打远程；
把脚本写到 workspace/exploit.py 并执行，把关键输出贴给我。
```

## 例 2 · Android APK：让 jadx 变成模型的工具

**前提**：`jadx-gui` 打开目标（插件监听 8650）；插件 jar 在 `~/.jadx/plugins/`；`mcp.json` 里有 stdio 的 jadx 服务端（见 02 文档配方）。

**侦察开场**

```
用 mcp 的 jadx 工具做侦察：先取 AndroidManifest，再列出主应用类名，
然后回答：这个 app 的入口 Activity 是什么、有没有 native 库。
```

实测输出（真实 APK）：

```
get_android_manifest → package="com.securevault.locker"  versionName="2.1.0"  compileSdk=34
get_main_application_classes_names → MainActivity / NativeBridge / R…
```

**定位可疑点**（注意 jadx 的搜索参数名是 `search_term`）

```
用 jadx 搜出名字里含 flag / password / decrypt / native 的类与方法；
对命中的类取反编译源码，重点看有没有 System.loadLibrary 和硬编码字符串。
```

实测片段：

```java
public class NativeBridge {
    static { System.loadLibrary("native_crypto");
             f1300a = new int[]{5, 12, 3, 14, 9, 0, …}; }
}
```

**接着做交叉验证**（jadx 与 IDA 一起用 —— 这是这套工具链最有价值的地方）

```
这个 so 库我也用 IDA 打开了：把 jadx 里 NativeBridge 调用的 native 方法签名列出来，
再用 ida 工具在 so 里找到对应函数并反编译，两边对照给我结论。
```

## 例 3 · Web 目标：让 Burp 变成模型的工具

**前提**：Burp 已加载官方 MCP 扩展并 Enabled；`mcp.json` 里用官方代理：

```jsonc
"burp": { "command": "java",
          "args": ["-jar", "…\\mcp-proxy-all.jar", "--sse-url", "http://127.0.0.1:9876"] }
```

**前提检查**：Burp 的 MCP 页签里，**Require approval for HTTP requests** 若开着，第一次请求可能会等你在 Burp 里点确认；想省事就关掉它，或在 **Auto-Approved HTTP Targets** 填目标域名。

**发请求 + 看返回**

```
用 mcp 的 burp 工具向 http://<授权目标>/ 发一个 GET，
把状态码、Server 头、以及响应前 20 行给我；不要做任何带攻击性的请求。
```

实测（示例目标）：

```
send_http1_request → HTTP/1.1 200 OK
  Server: cloudflare
  X-Forwarded-For: …（Burp 加的，说明请求确实走了 Burp）
```

**用 Burp 的能力做后续**（这些是 Burp MCP 的独特价值）

```
把刚才这个请求送进 Repeater；然后读 Burp 的代理历史，告诉我这个域名下都出现过哪些路径。
```

```
对 /login 这个路径，用 base64/url 编码工具准备好三种 payload 变体，
只发到靶场（127.0.0.1 或授权域名），把响应差异列成表。
```

**安全提醒**：Burp 的工具是**真实发包**的。把"只在授权目标上操作"写进角色提示词；权限页里也可以把网络权限收紧。

## 例 4 · 子智能体：让父 Agent 派人并行干活

**前提**：角色开了委派（见 02 文档第 6 节），并且有至少一个子角色可用（例如 `ctf-recon`）。

**提示词**

```
先读一下工作区里的 primes.py（用 read），然后用 delegate_task 派 ctf-recon
去查「RSA 小公钥指数攻击」的常见做法；你自己继续分析 primes.py 的结构，不要等它。
```

**你会看到（实测过程）**

1. 父先读文件（审计闸门要求它至少动过一次手，否则派活会被拒）；
2. 顶部出现标签：`agent-1 · ctf-recon · 运行中 · 已派…`；
3. **父这一轮很快就结束了**（3~30 秒），输入框回到"发送"——这是正常的：它不等；
4. 子智能体继续跑，你可以点标签切过去**只读**看它的会话（它的任务以一条"已发送消息"的形式在会话流里）；
5. 子智能体结束后，结论作为一条消息合并进父会话，父**自动开始新一轮**并复核结论；
6. 复核后父会说清"采纳了什么、否掉了什么"。

实测里父的原话（很能说明它的工作方式）：

> 报告只读了工作台清单，清单里确实没写 gmpy2，但我实测：gmpy2 2.2.1（import 成功）……
> 报告在这点上犯的正是「把清单当保证」的错误，我按实测纠正。
> 后半条我没验，暂时不采纳。

**停掉不再需要的子智能体**（父已拿到答案时）

```
题目已经解出来了，用 delegation_stop 把还在跑的子智能体停掉。
```

也可以在标签页上直接点 **✕**；主 Agent 报出候选 flag 时（`stopOnFlag`）系统也会自动停。

## 例 5 · 权限、停止与恢复

| 场景 | 操作 | 期望行为 |
|---|---|---|
| 某工具总是要问 | 权限页 → 给这个角色"允许"，或开 30 分钟**临时授权** | 到期自动收回；页面能看到"最终生效的权限"和算法 |
| 想立刻打断 | 输入框右侧「停止」 | 立即停；时间线显示中性「已中止」，**不会**报红错 |
| 想让它自己收敛 | 角色 → 任务循环：最多 3 轮 / 30 分钟 / 到限"先总结再停" | 到限后它先给结论再停，而不是硬中断 |
| 上下文快满 | 角色 → 自动压缩（或手动压缩指令） | 走 RPC 压缩，环上的占用会刷新 |
| 换一批工具 | 改角色工具清单后**新建会话** | 工具集只能在启动时定，界面会提示 |

## 例 6 · 排查"'它到底被告知了什么"

这一步是这套工具"可追溯"的关键，出问题先做这个，比反复试提示词有效得多：

1. **提示词分段**（纯文本，可逐字读）
   ```
   bin/.pi/roles/prompts/<角色>.md            角色提示词（你自己写的）
   bin/.pi/roles/prompts/<角色>.env.md        环境清单（每次启动按实测重写）
   bin/.pi/roles/prompts/<角色>.delegation.md 委派说明（按委派配置生成）
   ```
2. **会话原文**（Pi 的 JSONL，一行一个事件）
   ```
   bin/.pi/sessions/<工作区编码>/<时间戳>_<id>.jsonl     主会话
   bin/.pi/agents/agent-N/sessions/*.jsonl              子智能体会话
   ```
3. **界面侧的原始事件观察器**：对话里那些折叠行（`bash · …`、`思考`、`agent_settled · …`）都能展开看原始记录。
4. **应用运行日志**：`bin/.pi/gui-log.txt`（谁被派出去、什么时候被停、为什么）。

## 附：几条让结果更稳的提示词习惯

| 习惯 | 例子 |
|---|---|
| 先侦察再动手 | "先复述已知条件，再列最可能的三个方向，然后只验证第一个" |
| 要求可复现 | "把命令和输出都贴出来；失败也留痕" |
| 要求交叉验证 | "结论必须能被你自己复现一遍；引用别人的结论要标注来源" |
| 给边界 | "只在 127.0.0.1 上测试；不要碰其它主机" |
| 让子智能体干"边界明确"的活 | "查资料 / 复核一个结论 / 试另一条路线"——不要派"帮我把这题解了" |
| 分阶段交付 | "先把输入输出对拍清楚，再写 exploit" |
